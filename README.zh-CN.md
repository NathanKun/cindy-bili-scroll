# 刷B站（cindy-bili-scroll）

[English](README.md) · **简体中文**

替你在 B站上刷一轮：刷首页推荐或按关键词搜索 → 读字幕判断值不值得看 → 写一份 Markdown 日报；按你的设置决定要不要留一条评论并 @ 你、收藏、私信投递。

另有一条**回复车道**：只处理谁回复了你的评论、谁 @ 了你。它有自己的检查次数和回复额度，和刷视频那条车道互不吃额度。1.5.0 起两条车道共用**一条**自动化任务：闸门只判「这一拍要不要叫模型」，做哪件由插件判。

移植自 [c1overzz/dsh-bili-scroll](https://github.com/c1overzz/dsh-bili-scroll)（MIT），按 Cindy 插件的能力边界重新实现，不是逐行翻译。功能对照见下面的「和原版的差异」。

## 它做什么

1. 取候选：开关打开时由伙伴自己决定这一轮搜什么；关闭时填了关键词就按你给的词搜（一轮一个词），没填就刷你这个账号的首页推荐流。排除词命中的直接过滤。
2. 判重：先读自己的判重表（`seen.jsonl`），刷过的跳过，并把这件东西上一轮写给自己的判断一并带回来（见下面「视频记忆」）。
3. 细看：一条条读字幕原文判断。没有字幕轨的视频记「跳过（无字幕）」，不会硬猜。
4. 写日报：挑中的每条写一段到 `out/<日期>.md`，这一段第一行固定是 `### BV号`——插件靠数这行核对每日额度。卡片「卡片」页签会把它渲染成带封面和档位标签的卡片墙，可按值得看 / 可以看 / 不值当筛选、按标题搜索。
5. 可选互动：评论（可 @ 你）、收藏、私信投递。评论 / 私信按设置有额度上限，评论发之前还有风格闸门；收藏一轮最多一条、一天最多八条，只在设置里选了收藏夹后才可用。这三个工具不逐次弹确认——设置关着就发不出去，设置开着就等于你授权了这一轮按额度发。
6. 收尾：一轮结束调 `bili_round({action:"finish", roundId})`（**roundId 用开头那次 `bili_round` 返回的值原样回传**）把这一段这一次自动轮记成跑成；再调 `bili_verify()` 回头看一眼评论是否真的公开可见，结果写回**那条评论自己那天**的日报「评论复核」一节。

**回复别人不在这条线上**：它是互动轮（`bili_inbox({action:"start"})`），见上面「自动运行」。日报轮里 `budget.reply` 恒为 0。

## 视频记忆

判重表本来就是「刷过什么」的清单。1.3.1 起，每个条目还可以带一句**笔记**：这条到底讲了什么、为什么跳、这个 UP 的成色如何。**笔记由模型自己写**，插件只负责存和带回来——所以这份记忆带着跑这一轮的那个伙伴的口吻和标准。

一句话笔记（`note`，≤200 字）在三个地方起作用：

- 下一轮开头 `bili_round` 返回 `memory`：最近 12 条带笔记的记录（BV 号、标题、UP、当时判了什么、那天是几号），加上按 UP 折叠的「上次怎么看这个 UP」（最多 6 个，按记过笔记的条数排序）。
- `bili_browse` 给刷过的候选挂上 `note`，给同一个 UP 的其它视频挂上 `upNote`。所以第二轮拿到一条新视频时，它已经知道「这个 UP 上次被我判成什么样」。
- 卡片「判重表」页签多一列「当时的判断」，不用翻文件就能看它每轮想了什么。

权重是写死在章程里的：**旧笔记是它自己的判断，不是别人说的**——高于标题和简介，低于这一轮真正读到的字幕。跟旧笔记冲突时按这次的判，但要在新笔记里写清为什么改，否则下一轮会看到两个互相矛盾的自己。

判重表读不到时 `memory` 是 `null` 而不是空对象：给一份空记忆等于告诉模型「我以前什么都没想过」，比不给更糟。

两点要知道：

- **只追加，不自动清理。** 笔记的上限（每条 200 字、每轮只带 12 条 + 6 个 UP）保证它不会撑爆上下文，但文件本身会一直变长。想瘦身就在插件数据目录里手动整理 `seen.jsonl`——删掉整个文件等于同时也忘了「刷过什么」。
- **记忆跟着插件走，不跟着伙伴走。** 判重表在插件私有数据目录里，跟这一轮是哪个伙伴跑的无关。换个伙伴来跑，它看到的是同一份视频记忆，只是会用自己的口味去接着判。想让不同伙伴有不同标准，靠它们各自的 SOUL 和记忆，不是靠这条。

## 第一步：登录

B站 的账号能力（AI 字幕、评论、收藏、私信）都要登录。**凭证永远不会经过对话。**

登录在**插件详情页 →「自定义设置」→「登录」页签**（第一页）。两种方式，任选一种：

- **扫码**：点「生成二维码」才去 B站 要一张——不打开这一页、不点按钮，就不会调用任何登录接口。用手机 B站 App 扫，确认时选「记住我 / 长期」。
- **按名字填三个 Cookie**：三个独立输入框 —— `SESSDATA`（必需）、`bili_jct`（要评论 / 收藏 / 私信就填）、`DedeUserID`（可选）。名字写在每栏的标签上，填完之后照样看得见这一栏是什么。**每栏只填值，不要带「名字=」**，名字由插件拼回去（真的多粘了 `SESSDATA=` 也会被认出来削掉）。
  整段请求头也可以直接粘进任意一栏：插件会认出里面的三个名字，自动分到各自的栏里，粘完可以核对再提交。提交后三栏立刻清空。

两种方式都是先问 B站「这是谁」，认得过才落盘；认不过就报错、不动原来的凭证。这段值只在设置页和你本机之间走，不进对话、不回显、也不会出现在报错里。

同一个页签里还有两个按钮：「核对一下」会真的问一次 B站「这段凭证还认不认」（平时打开设置页只读本机凭证，不打接口）；「退出登录」要点两次才执行。

至少要有 `SESSDATA`；没有 `bili_jct` 的话只能刷、不能评论 / 收藏 / 发私信（插件会当场提醒）。成功后凭证写进插件自己的数据目录（`credential.json`），页面上只显示昵称和等级。

登录只在设置页做。1.3.8 起卡片上的「登录」页签已经删掉：卡片每发一次工具调用，宿主都可能当成一张请求卡片刷进对话；而且插件一更新，已经打开的卡片就失效、又得重新扫。这两点放在「要等手机扫码」的流程里都不划算。

要退出登录也可以在聊天里说「退出 B站 登录」——插件会调用 `bili_config({action:"logout"})` 并让你确认。

## 自动运行：一条任务、一个闸门，做什么由插件判

原版的「自主」是 `setInterval` 每分钟跑一次纯脚本判断，该跑才 spawn 一个会话。Cindy 里等价的东西是**自动化任务的前置检查脚本（preRunHook）**：脚本零 token 地判「这一刻要不要叫模型」，放行（exit 0）才开一轮，跳过（exit 2）就不叫、不进账单。

1.5.0 起只有**一条自动化**，两类活共用它。三层，各回答一个问题：

```
闸门（Node 脚本，0 token） 这一拍有没有活？        → exit 0 / exit 2
分派（插件 bili_round）     刷视频、回回复，还是都不？ → mode=report / inbox / none
执行（模型）                照拿到的章程做那一件事
```

1. **闸门** `schedule/precheck.mjs`，挂在任务上当前置检查。它读插件写出来的镜像（`%APPDATA%\Cindy\duty\cindy-bili-scroll/{config,state}.json`），只判**要不要**叫模型。它故意不判「做哪件」：preRunHook 的 stdout 不会进模型上下文，说了也没人听。
2. **分派** 模型第一步调 `bili_round({action:"start"})`。插件用**刚读到的记账**跑同一个判定函数（`schedule/decide.cjs`），所以它是权威，回答 `mode=report`（带刷视频章程）、`mode=inbox`（带回复章程，而且这一次检查已经替你开好了，不用再调别的工具）或 `mode=none`。
3. **执行** 模型照这份章程往下做。

闸门是保守粗筛：它看到的是上一次同步的镜像，可能差几分钟。它放行、插件转头发现没活，代价是这一次白跑（最多把这一槽的 3 次尝试花完）；插件发现没活时会顺手把镜像刷新一次，所以下一拍闸门也跟着停，不会每拍都白叫。**绝不会多发一条内容。**

为什么从 1.4.0 的两条合成一条：两条 cron 意味着两个模型会话可能同时动同一个账号，而插件分不清是哪个模型在调工具，「回复轮只许回复」就只能写成提示、拿不到结构保证；而且「哪个任务挂哪个 hook」本身就是一整类配错的可能。

### 为什么 cron 要「反复敲」

Cindy 的调度器**不补跑**：错过的 cron 点就是没了。于是「一天两轮」有两种做法：

- 建两个窄窗口任务（8:00、18:00）：**电脑睡着/关着就当天漏掉**；
- 一个宽任务反复敲（每 30 分钟，或者更密），由闸门决定这一敲算不算一轮：**只要那段时间电脑醒着，就不会漏**。

本插件选后者，所以刷视频这条车道用的是**按时段配额**（每一段各记各的账），而不是「今天跑成过几轮」：早上那一段只放它自己的一轮，晚上那一段留着晚上用。这样就同时拿到了「分散」和「不怕漏拍」，又不会像按天计数那样，一个开机后十分钟就把全天轮次跑光。

### 时段配额怎么配

设置页「日常 → 时段配额」里一条条填：`开始 – 结束 × 这一段最多几轮`。例如

| 开始 | 结束 | 轮次 |
| --- | --- | --- |
| 06:00 | 10:00 | 1 |
| 18:00 | 24:00 | 1 |

就是「早上一轮 + 晚上一轮」，两段互不吃额度。要点：

- 时段是**一天之内的左闭右开区间**（`06:00–10:00` 含 06:00、不含 10:00）。**不跨零点**：要覆盖 22:00–02:00 就拆成 `22:00–24:00` 和 `00:00–02:00` 两段（各自算额度）。
- 段之间不能重叠；不合法或重叠的段会被丢掉。一段都不合法时退回「`00:00–24:00` ×1」，自动任务不会因此停摆。
- cron 什么时候敲是你的自由，只要**比配额密**：每拍都是零 token 的脚本，只有放行时才叫模型。插件预填的任务是「每 30 分钟」（宿主允许预填的最小间隔），对宽一小时以上的时段够用；想要 `*/5 * * * *` 那种密度就自己在任务里把频率改成 cron 表达式（或者跟 Cindy 说一句让它改）——闸门仍然只会放 N 次。
- 手动轮（聊天里说「现在刷一轮」）不受时段限制，也不占任何段的额度。

### 闸门判什么

一张清单，两条车道。**规则只有一份实现**（`schedule/decide.cjs`）：闸门 `import` 它，插件经随包 worker 找它——`duty/decide`（这一拍做什么）、`duty/segments`（洗完的段表，用来写 `config.json` 镜像）、`duty/layout`（此刻在哪一段、还剩几轮、这一槽试过几次、互动检查今天还剩几次）。`main.js` 跑在沙箱里没法 `require`，所以它是**问 worker**，而不是自带第二份：里面没有 `parseClock`、`normalizeSegments`、`attemptsOf`、`inboxLimits` 之类的东西。谁把副本抄回去，`tests/test-main-gate.cjs` 第 12 节就直接失败；段表的两种形态（判断用的分钟数 / 存储和展示用的 `HH:MM` + key + label）是否出自同一次清洗，由 `tests/test-decide.cjs` 盯着。唯一有意的差别：插件调 `decide` 时会传 `claim`，脚本不传——脚本上一次的放行已经花掉了，插件正要用的那次才不算「之前试过」。

只要**任一条**车道有活就放行：

- **刷视频**：已登录、没有一轮在跑、今天的挑片额度（`perDay`）没满（`perDay = 0` 是「不自动限流」）、现在在某一段里、这一段今天还没跑成 `rounds` 轮、这一轮还没试满 3 次
- **回回复**：已登录、「允许回复别人的追问」开着且「每天最多检查几次」大于 0、没有一轮在跑、没有一次检查在跑、今天的检查次数没用满、离上一次检查过了最小间隔

两条都没活就跳过，并说清原因：

- 没登录（最省钱的一条：没登录就永远不叫模型）
- 已经有一轮在跑（12 分钟内的锁），或已经有一次检查在跑（15 分钟内的锁）——单车道就是同一时刻只做一件事，两个方向都成立
- 这一段跑满了 / 这一轮试满 3 次了（同原版 `MAX_WINDOW_TRIES`）/ 今天挑满了
- 检查次数用满了，或还没过最小间隔

只有 `bili_round({action:"finish"})` 才算跑成一轮，写日报本身刻意不算：写了两条然后崩了的那一轮应该被重试，而不是把这一段的次数用掉。回复那边，**用过的次数 = max(插件记的, 脚本记的)**：插件记「真的开起来了」，脚本记「我放行过」——模型崩在半路的那一次也是一次真账单，不能不算。

它**判断不了「收件箱里有没有新消息」**：脚本拿不到 B站 凭证，也不该在这里发网络请求。所以回复这条车道的成本模型是「一天被叫醒 N 次，每次拉一次收件箱，空就立刻收尾」，N 由「每天最多检查几次」决定。这是这个设计里唯一的、也是明说的代价。

### 一次检查 = 什么

一次 `bili_inbox({action:"start"})` 到对应 `finish` 的完整过程（自动那一拍是同一条路径：`bili_round` 分派到 `mode=inbox` 时已经替你开好了）。它跟「有几个人回了你」无关：**哪怕收件箱是空的，那一轮模型也是真被叫醒了**，所以照样算一次、照样占名额。收件箱为空时 `start` 会直接收尾（返回 `nothing:true`，不建锁），模型不用再多调一次 `finish`，这一拍就到此为止。

### 镜像文件

脚本读不到插件的私有目录和 `/kv`，所以插件每次开跑 / 改设置 / 写日报之后，把判断需要的**最小事实**镜像到：

| 文件 | 内容 | 谁写 |
| --- | --- | --- |
| `%APPDATA%\Cindy\duty\cindy-bili-scroll\config.json` | 只有闸门要的几个设置（`segments` / `perDay` / `replyToComments` / `inboxChecksPerDay` / `inboxMinGapMin`）；关键词、排除词、口吻提示、@ 昵称、私信收件人留在插件私有目录 | 插件 |
| `%APPDATA%\Cindy\duty\cindy-bili-scroll\state.json` | 今天挑了几条、各段各自跑成了几轮、各段各轮试了几次、登没登录（不带昵称）、有没有一轮在跑；回复那本账（`inboxChecks` / `inboxLastAt` / `inboxLock`）；另有闸门自己记的 `hookStarts` / `hookDay` / `hookAt` / `inboxHookTries` / `inboxHookDay` / `inboxHookAt` / `lastSkip` | 插件为主，后面那几个由脚本写 |

方向上基本是单向的：**插件写、脚本读**，例外只有一处——闸门放行时会把**自己的**计数加一（刷视频那条写 `hookStarts[段内槽位]`，回复那条写 `inboxHookTries`）。因为「放行」之后模型可能压根没跑到工具，不在这里记，cron 就会每一拍重试到天荒地老；插件同步时原样保留这些键，并把合并后的值**取回来**记进自己的 state，让两边算的是一个数。`hookDay` / `inboxHookDay` 记的是这个计数属于哪一天：昨天试满三次不该把今天挡死，跨天时两边都从零开始。

**设置页点保存会顺手同步一次镜像**（页面通过 `/wake` 叫起插件，再让它重写这两个文件；保存后的提示会说成没成）。这一条是必需的，不是优化：镜像是插件写的，而插件只在被调用时写——设置页把互动轮从「关」改成「开」之后，闸门脚本读到的仍是「关」，它就一直跳过，模型永远进不来，插件也就永远没有下一次调用去改写镜像，两个方向都卡死。同步失败（插件没醒、宿主太旧）时，在聊天里说一句「刷B站 看设置」也会重写一遍。手改这两个文件会在插件下次运行时被覆盖。

**1.6.2 起镜像不在家目录根下。** 1.6.1 及更早写在 `~/bili-duty/`（Windows 上就是 `C:\Users\<你>\bili-duty`）。搬家是因为 Cindy 给插件的存储只有两种：`/kv`（设置）和 `cindy.fs root:'data'`（私有目录、卸载即回收）。家目录那份不在其中，是随包 Node 进程直接写盘的——而家目录会被各种同步 / 备份工具扫进去，偏偏这两个文件是账号的活动记录。现在按平台放：Windows `%APPDATA%\Cindy\duty\cindy-bili-scroll`，macOS `~/Library/Application Support/Cindy/duty/cindy-bili-scroll`，Linux `$XDG_DATA_HOME/cindy/duty/cindy-bili-scroll`。插件和闸门**各自算出同一个路径**，不靠配置传。升级后第一次运行（插件或闸门谁先醒谁做）会把旧位置的两个文件拷过来，**旧目录不自动删**；如果你手改过旧文件，删之前先确认新位置那份是你想要的。

### 怎么搭 —— 只要一条任务

**hook 用安装目录里的脚本，用绝对路径，不要复制副本。**

```
"<node.exe 的绝对路径>" "<插件安装目录>/schedule/precheck.mjs"
```

Windows 上形如 `"C:\Program Files\nodejs\node.exe" "C:\Users\<你>\AppData\...\cindy-bili-scroll\schedule\precheck.mjs"`（两段都要带引号，路径里可能有空格）。cwd 由任务自己决定，脚本不依赖它——`decide.cjs` 和 `gate.mjs` 都是相对 `precheck.mjs` 自己找的。

为什么不用副本：副本会随插件升级**静默过期**，继续按旧规则判断，而你毫不知情；绝对路径断了是响亮失败（前置检查失败 → 任务不跑 → 你能收到通知），符合「宁可少跑，不要按错规则跑」。(1.3.x 的 README 教的是复制到任务目录，那套做法已经废弃。)

这条任务其余配置：

1. agent 模式，`silentWhenIdle: true`；
2. 频率：预填的是「每 30 分钟」（宿主对预填间隔的下限）；想要 `*/5 * * * *` 就在面板里改成 cron 表达式，或只在你关心的时间段敲——这一拍变成什么由闸门决定，敲得再密也只是零 token 的脚本；
3. 挂上前置检查脚本 `precheck.mjs`。**没有第二条任务、也没有第二个 hook 可以挂错。**

在聊天里说「设成每天自动刷」或「帮我盯着回复」，打开的是同一条任务的预填面板。

想手动验一次闸门：`node "<安装目录>/schedule/precheck.mjs"`，退出码 0 = 放行、2 = 跳过，跳过时会把原因打在 stdout。加 `--home <目录>` / `--now <ISO时间>` 可以拿一份假的值班文件试。

### 升级与迁移（1.4.0 → 1.5.0）

1.4.0 给了你**两条**自动化（刷视频一条、「回复互动」一条，各挂各的 hook）。1.5.0 只要**一条**：

**先做这一步：删掉「刷B站 · 回复互动」那条任务。** 留着不会重复发内容（同一时刻只有一把锁放行，第二个会话拿到的是 busy），但也不是白跑一次那么简单。两个 hook 是先后读同一份 `state.json` 的，各自 +1：

- 日报每个「段#轮」的 3 次尝试被**双倍消耗**，重试预算只剩一半；
- 如果第一个脚本刚好用掉这一槽的最后一次放行，第二个会改判并**放行互动**——那一次检查额度被记掉，却没有真的检查（`检查次数=2` 的设置下当天只剩一次）；
- 「两次检查至少隔几分钟」设成 0 时，同一次检查可能被记成两次，同理少一次；
- 两个模型会话同时醒来时，第二个只会拿到 busy，但账单已经产生。

删掉它，剩下的那条才真的是单车道。

然后处理**留下刷视频那条**：

1. **把它的前置检查脚本指到 `<安装目录>/schedule/precheck.mjs`**（绝对路径，见上）。路径已经指在那里的话不用改——文件名没变，只是它现在同时管两条车道。
2. **更新这条任务的提示词。** 1.4.0 的提示词只认识「刷视频」这一种结果，不会按 `mode` 分支。两条路任选：
   - **换一条新任务（推荐）**：在聊天里说「设成每天自动刷」，插件打开新建面板并预填新提示词 → 保存成「刷B站 · 自动运行」→ **给这条新任务挂上同样的 hook** → 再删掉原来那条旧的（否则又变成两条）。
   - **改原来那条**：在自动化面板里直接编辑它的提示词，把新面板给出的那段贴进去（新面板**取消、不要保存**，否则会多出一条）。hook 路径不用动。
   - 只保存了新任务却忘了挂 hook，会得到「一条有闸门 + 一条没闸门」：没闸门那条每 30 分钟无条件叫模型，比升级前更贵。
3. `schedule/precheck-inbox.mjs` **还会随包发一个版本**，它只是转调 `precheck.mjs`，所以旧任务的 hook 指着它也不会突然失败。但它已经**不再是「只做互动」的闸门**：它同样会放行刷视频那一拍。这也是要删掉旧任务的理由之一。
4. 设置不用迁：时段配额还管刷视频，「允许回复别人的追问」「每天最多检查几次」「两次检查至少隔几分钟」还管回复——只是它们现在共用同一条任务，而不再各自一条。
5. 1.3.x 的旧设置键（`peakValley` / `noon` / `night`）照旧静默忽略，`autoRoundsPerDay` 照旧迁成一段整天。

如果你是从 1.3.x 一路升上来的，另外还有几条：

- **三个时段开关早就没了**（「只在指定时段自动刷」「中午 12:00–14:00」「夜间 18:00–09:00」）。时间控制权只归 cron：那两个勾选框和 cron 抢同一件事，而且打开总开关却不勾任何一段会变成「只有周末跑」。旧键留在 `/kv` 里也不会报错（读的时候直接忽略），下次保存设置时会一并清掉。
- **回复早就搬出了刷视频轮**：升级后需要打开「允许回复别人的追问」、把「每天最多检查几次」设成大于 0。默认是关的——升级不该悄悄开始叫模型。
- **hook 路径要重新指**：如果照 1.3.x 的 README 复制过 `precheck.mjs` 副本，请把它改成安装目录的绝对路径，或者干脆删掉那条任务重搭一条。旧副本能读到兼容字段（不会乱跑、不会超配额），但它不懂时段配额：它会以为「任何时候都能跑」，于是可能在时段外把模型叫进来——`bili_round` 会拒绝，可拒绝不会同步，旧副本就会按它自己那 3 次尝试一直敲到放弃，那一天的轮次也就没了。
- 插件镜像里为旧副本保留的 `runs` / `autoRoundsPerDay` / `windows` **这一版继续留着**（每拍几十字节），因为正是它们让 1.3.x 的副本不会每拍都放行；等确定不会再有人在跑旧副本时再删。

## 工具

| 工具 | 作用 | 审批 |
| --- | --- | --- |
| `bili_round` | 每轮开头，也是自动运行的第一步：返回 `mode` —— `report` 时给额度、预算、当前时段还剩几轮、设置、判重记录、`memory`（最近的笔记 + 每个 UP 的上次判断）、roundId 和刷视频章程；`inbox` 时说明这一拍该回回复，并已经替你开好了这次检查（`inboxId`、条目、回复额度、互动章程都在返回里）；`none` 时这一拍没活。`action:"finish"` + `roundId` 收尾并把这一段的自动轮推进一格（token 对不上说明这一轮已超时，会拒绝执行） | 沿用任务权限 |
| `bili_browse` | 推荐流或关键词搜索（带 `seen` 标记；见过的挂 `note`，同 UP 的挂 `upNote`） | 沿用 |
| `bili_detail` | 视频详情 + 字幕（`subtitle:false` 只取表层信息） | 沿用 |
| `bili_comments` | 热门评论（含楼中楼，带回 `rpid`） | 沿用 |
| `bili_report_append` | 追加当天日报 | 沿用（写插件私有目录） |
| `bili_seen` | 不带 `record` 读判重表，带 `record` 写一条（`note` 可选，≤200 字，是写给下一轮的自己的话） | 沿用 |
| `bili_comment` / `bili_reply` / `bili_favorite` / `bili_dm` | 对外说话（用你本人账号）。`bili_reply` 属互动轮，要 `inboxId` | **免逐次确认**（设置闸门说了算，见下） |
| `bili_inbox` | 收件箱，也是互动轮入口：不带 `action` 只读一眼（不记账）；`action:"start"` 开一次检查（返回 `inboxId`、条目、回复额度、互动轮章程）；`action:"finish"` 收尾 | 沿用 |
| `bili_verify` | 回头查最近发的评论是否公开可见，写进日报「评论复核」 | 沿用 |
| `bili_config` | 读 / 改设置（含 `segments` 时段配额、互动轮配额）；`action:"logout"` 清凭证 | **逐次确认** |
| `open_view` | 打开卡片（`intent`：日报 / 卡片 / 判重表 / 新建自动化面板；旧的 `schedule-inbox` 还在，但打开的是同一条任务——没有第二条可建了） | 沿用 |
| `view_data` | 只给卡片调用（`kind`：日报 / 判重表 / 卡片 / 收藏夹）。登录没有工具了：设置页用 BroadcastChannel 把活递给插件后台 | — |

> **「免逐次确认」是什么意思。** 跑一轮要用到的工具在 `ghost.json` 里都是 `approval: "auto"`——四个对外写工具（`bili_comment` / `bili_reply` / `bili_favorite` / `bili_dm`），加上这一圈读和落盘：`bili_round` / `bili_browse` / `bili_detail` / `bili_comments` / `bili_inbox` / `bili_verify` / `bili_report_append` / `bili_seen`。自动化的权限模式不在任务定义里（`schedule_create` 没有这个字段），由宿主默认跑，所以这些工具必须自己声明免确认，否则哪天任务被设成「询问」档，凌晨那一轮会卡在一张没人看的卡片上。安全性全部压在设置闸门上——设置里没开、额度用完、同一视频发过、风格闸门不过、正文有 @ 或超长，插件都会在本地直接拒，请求根本不会发出去。代价是：**如果模型误判，评论会以你本人的名义发出去**，事后只能自己删。想收回这个授权，把对应的设置关掉就行（关掉之后工具仍然在，但调了会被拒）。
>
> `bili_config` 仍是 `"each-call"`：改设置、退出登录这类动作永远逐次确认。
>
> 版本更旧的 Cindy 不认 `approval: "auto"`，会照旧逐次弹确认——那是更严的一侧，不会更松。

> Cindy 对单个插件的工具数上限是 16 个。为了不砍功能，把成对的工具合并了：`bili_video`+`bili_subtitle`→`bili_detail`，`bili_seen`+`bili_seen_append`→`bili_seen`（凭 `record` 区分读/写），`login_start`+`login_poll`→`login`（凭 `action` 区分，1.3.0 起还多一个 `cookie` 动作；1.3.8 登录搬进设置页之后这个工具整个删掉了），`bili_logout`→`bili_config({action:"logout"})`，一轮的开跑与收尾合并成 `bili_round({action})`；`bili_status` 的内容本来就在 `bili_round` 的返回里，删掉；`bili_install_schedule` 换成 `open_view({intent:"schedule"})`（它只是打开面板，不值得占一个名额）；`bili_frames`（故事板地址）没有模型侧价值，删掉。

> **写入都带上 roundId。** `bili_report_append`、`bili_seen`（带 `record` 时）、`bili_comment`、`bili_favorite`、`bili_dm` 都接收开头那次 `bili_round` 返回的 `roundId`；`bili_reply` 接收的是互动轮那次 `bili_inbox({action:"start"})` 返回的 `inboxId`。插件靠它判断这条写入属于哪一轮、哪一天、算不算自动轮——一轮读十几条字幕很容易超过 12 分钟的锁，锁过期后两小时内写进来的条目仍然记在那一轮头上。带了一个对不上任何一轮的 id（被新一轮接管、这一轮已收尾、锁超过两小时）会回 `ROUND_MISMATCH` / `INBOX_MISMATCH`，既不会记到别人头上，也不会被悄悄当成一次临时写入。不带 id 的调用按「临时写入」处理（会被算进当时在跑的那一轮，所以会占它的额度）。

> 同一个 BV 再写一遍不占新额度；`### BV…` 里的 id 后面必须跟空格或换行——多一位、或者紧跟下划线/标点都会被拒，而不是截断成另一个视频。

> **评论 id 一律按字符串传。** B站 的 `rpid` 是 64 位整数，JavaScript 的 `Number` 过 2^53 就开始丢末几位——拿丢过精度的 id 去回复会挂到别人的楼里，复核时也会误报「没查到」。所以 `bili_reply` 的 `aid` / `rpid` / `root` 在工具 schema 里就是字符串，`bili_comments` / `bili_inbox` 返回的也是字符串，原样传递即可，不要转成数字。

## 和原版的差异

**直接搬**：日报格式与 `### BV号` 约定、判重表、每日额度、手动冷却、评论风格闸门（`@ X`→`@X`、套话开头、与历史评论/热评的 bigram 相似度）、推荐流/搜索/视频信息/字幕/评论这些接口形状（对照 `bilibili-api-python` 17.4.2 的 `data/api/*.json` 复刻字段）。原版的「峰谷窗口」是按时间过滤的开关，1.4.0 换成了按段的配额——理由见上面「自动运行」：cron 不补跑，光过滤时间救不了漏拍。

**改写，以及为什么**：

- **B站 数据获取**：原版用 Python `bilibili-api`，Cindy 插件带不了 Python 运行时；依赖也不许在用户机器上现装——不能在安装或首次运行时跑 `npm install` / `npx` / `postinstall`，依赖必须在制作阶段打进 worker（打包器会跳过 `node_modules`）。这里一个都不需要：原生 `fetch` + `node:crypto` 做 WBI 签名，`finger/spi` 拿 buvid3/4 绕开 HTTP 412，被风控时换 buvid 重试一次、请求间隔 ≥300ms。
- **扫码登录**：原版在设置页/终端扫码。Cindy 里凭证不能进聊天，所以二维码画在设置页里（随包 MIT 的 `qrcode-generator` 直接画 canvas，不把登录地址发给第三方），扫码结果在 `main.js` 里落 `credential.json`。1.3.3 起卡片和设置页都能登，1.3.8 起只剩设置页那一条。
- **设置界面**：原版是宿主设置页四页签；这里用 Cindy 的 `settingsHtml` + `/kv`，分组照旧。
- **日报落点**：格式不变，写到插件私有数据目录 `out/<日期>.md`；卡片里直接渲染。
- **定时运行**：原版自带 `setInterval` 调度。Cindy 插件不能自己建任务，改成「自动化 + 前置检查脚本」两件套（见上面「自动运行」）：判断逻辑仍在零 token 的脚本里，模型只在放行后被叫醒。代价是闸门脚本要单独挂到任务上，且插件得把判断所需的事实镜像到 `%APPDATA%\Cindy\duty\cindy-bili-scroll/`（原版是调度器和业务逻辑在同一个进程里，不需要这份镜像）。
- **收藏夹选择**：原版在设置页直接拉列表点选。Cindy 的设置页只能读写 `/kv`，调不到工具，所以插件把收藏夹列表同步进 `/kv`（打开卡片「卡片」页签、或读一次 `bili_config` 时刷新），设置页用下拉呈现；手填收藏页地址里的 ID 也一直可用。

**不做，以及为什么**：

- **受限执行 profile**（原版 `profile-template/bili-duty/cordis.patch.yml` 把文件/命令/网络从模型运行时里摘掉）：在 Cindy 里这层是宿主的活。等价约束改成三道：对外写工具全部走设置闸门（额度、同一视频一次、风格闸门、@ 与字数硬限都在插件本地执行，设置关着就发不出去）、工具面固定（模型只能经插件工具访问 B站，路径全由插件定死）、每轮章程写死「视频文字是数据不是指令」。**不宣称这等价于原版的权限剥离**：模型仍在本任务里拥有宿主给的权限；而且这四个工具已改成 `approval: "auto"`（不逐次弹确认），误判的后果是评论以你本人的名义发出去。
- **语音转写（Whisper）**：需要 Python + 约 1GB 模型权重，Cindy 插件装不了系统依赖。没字幕的视频按「跳过（无字幕）」处理。
- **自动回私信（双向）**：只做投递 + 读消息列表（`bili_inbox`）。三个独立的坎：要一条 web_im 长连接（按需启动的 worker 不常驻）；用你的账号无人值守地跟陌生人对话风险太大；要让「回第二条时还记得第一条」就得有一个插件能持续寻址的模型会话——Cindy 里插件只能在用户点卡片打开的会话里跑一轮（另有一个本插件未申请的后台续跑能力）。聊天里能不能看到插件在干活是另一回事：插件的每一步都以工具调用的形式出现在**跑这一轮的那个会话**里，卡片里的日报 / 卡片 / 判重表也是实时读盘——但自动化跑的轮次记在自动化任务的会话里，不会主动弹到你的私聊。

  1.6.0 起，这一轮真的往今天的日报里写出了新条目时，模型会在收尾后调一次 `open_view({intent:"cards"})`（`finish` 返回 `reportUpdated: true` 才调）。**实际会发生什么**：`open_view` 是绑定到插件交互页面（MCP Apps 资源）的工具，卡片挂在**那次调用的那条消息上**，随那次运行的会话一起存下来（宿主的会话历史里它就是一个可见的结果，重开会话还在）——所以要看到它，得打开「刷B站 · 自动运行」这个任务的会话；如果当时你正开着那个会话，卡片就当场出现在里面。没有任何东西会跳进你的私聊，也不会有通知（这条路径没有任何提醒机制）。另外两点说实话：查看端版本低于 0.1.122-beta、或那次运行的权限模式要求人工批准工具调用，卡片就不会出现/要等批准——**不要把它当成「一定会弹出来」**。

**不做**：**看画面挑片**。原版在没有字幕时抽故事板帧来看。这一版只有 API 表里那条用不到的 `videoshot` 地址：没有请求函数、没有格子几何解析、不裁帧，也没有对应工具（零依赖 Node 本来也解不了 JPEG）。所以没字幕的视频只能靠标题和简介判断，章程里明确禁止据此声称看过画面。

## 已知限制

- **字幕依赖登录**：未登录时看不到 AI 字幕。实测匿名的 8 条搜索结果全部 `available:false`。不登录的话核心功能只剩标题/简介判断。
- **自己的评论自己看得见 ≠ 别人看得见**：B站 对审核中或被限流的评论只对发布者本人放行——同一条评论，用自己的凭证拉最新主楼能看到，换别人的账号（或匿名）就没了，@ 也不会有提醒。1.3.5 起复核会查两遍：用登录态一遍、不带登录态一遍，只有匿名那遍也查得到才写「公开可见」；只有你查得到时写「别人看不到：只有你自己看得见（审核中或被限流）」。
- **写接口未经真实账号验证**：评论 / 收藏 / 私信按 `bilibili-api-python` 的字段复刻。没有凭证时插件在本地就拒了（`NOT_LOGGED_IN`），请求根本没发出去，所以这些请求体**一次都没被真正验证过**；`-101` 只在「凭证文件在但已失效」时出现，而且它是身份校验失败、轮不到校验请求体。真正发出去是否成功要等真实账号跑一轮才知道。私信以是否拿到 `msg_key` 回执判断投递，没有回执就报 `sent=false`，不会假装成功。
- **收藏夹列表是缓存来的**：设置页是零桥沙箱页（只有 `/kv`，没有工具通道），自己拉不了收藏夹，所以下拉里显示的是插件上次同步到的列表。没同步过就只有空下拉，手填 ID 一样能用。
- **镜像有时差**：`%APPDATA%\Cindy\duty\cindy-bili-scroll/state.json` 在插件每次被调用之后更新，设置页保存时也会同步一次（插件没醒就同步不上，说一句「刷B站 看设置」可补）。一轮跑到一半时脚本看到的是上一次同步的快照——这是能力边界决定的，不是 bug。插件自己读不到 `state.json` 时**设置仍然会同步过去**，只有 `state.json` 停在上一份——宁可旧，也不写一份「今天什么都没干、没有轮次在跑」的空账让闸门多放行一轮。
- **极端情况下两边会互相盖掉一次写入**：闸门和插件的 `duty/sync` 都对同一份 `state.json` 做「读—改—写」，而插件是整份写回。方向有两个：
  - 闸门的增量落在插件「读」和「写」之间 → 那一次计数退回旧值，后果是**可能多叫一个模型**；
  - 插件的写入落在闸门「读」和「写」之间 → 闸门会把刚释放的锁 / 刚推进的段轮次写回去，后果是**这条车道被一把复活的锁按 12 分钟**（或那一槽被多放一次、插件回 `mode=none`）。
  闸门写之前会再看一眼文件有没有变过，变了就重读重合并，把第二个方向的窗口压到很小；没有加文件锁是故意的——这段代码跑在每一拍的前置检查里，为此加锁不划算。升级后**留着两条任务**会让两个方向都明显变多，这是要删掉旧那条的理由之一。
- **两条车道不会各自开始，而「只许回复」由调用方带的 token 判**：抢锁时两个方向都会再查一次对方的锁，所以同一时刻只有一个模型在**开始新的活**；而评论 / 收藏 / 私信能不能发，看的是这次调用带的是 `roundId` 还是 `inboxId`（`laneOf`）——锁过期了、或者一轮日报跑得比 12 分钟还长，都不会让互动轮里的写操作漏过去。
- **锁过期之后，两件活可以同时在跑**：日报锁 12 分钟、互动锁 15 分钟，都比「一轮读十几条字幕」该花的时间短。超过锁的时间还在干活时，另一条车道可以被放进来——它们各自按 token 分道，不会互相顶替，但「同一时刻只有一个模型在动这个账号」只在锁的时间窗内成立。这是有意的取舍：锁再长，一次崩在半路的轮次就会把车道堵到那个长度。
- 剩下的边界是：一次检查**收尾之后**仍然有工具调用进来、又没带 token 时，按「临时写入」处理——那时跟「使用者在聊天里让插件干活」是同一种情形，插件分不清是哪个会话在调它。
- **「首次放行」也有上限**：刚装、还没同步过镜像时，闸门会先放行一次（不然插件没机会把自己写出来）。这条逃生门**每天**最多 3 次；插件一直写不出镜像（凭证目录坏了、worker 起不来）时，闸门会停下并在任务记录里写清原因，而不是每一拍白叫一次模型。注意它是按天重置的：一个永远写不出镜像的安装，每天仍会被叫醒最多 3 次。
- **`network.hosts` 只约束 `cindy.fetch`**：随包 Node 工作进程用自己的网络栈直接连 B站（`*.bilibili.com`），`network.hosts` 里声明的是页面要加载的封面域名和这份实际访问范围。安装时列出的权限以安装页为准。
- **故事板**没做：只留了 `videoshot` 地址常量，不请求、不解析、不裁帧。
- **搜索/推荐** 都是 B站 有风控的接口：被 412 拦时插件会自动换 buvid 重试一次，仍失败就如实报错。
- **设置页与插件之间靠 BroadcastChannel**：设置页是零桥沙箱页（只有 `/kv`，没有工具通道，也不能直连 B站），所以「登录」这件事只能由插件后台去干。插件是按需拉起的，设置页会先叫醒它、再按 `reqId` 重发请求直到收到回执；插件那边按 `reqId` 去重，重发不会把同一件事干两遍（否则第二张二维码会作废第一张）。反过来，插件一直不应答时，设置页会明说「插件没有回应」——卡片里没有第二条路了（1.3.8 起登录页签已删）。

## 数据放在哪

| 位置 | 内容 |
| --- | --- |
| `/kv`（设置参数） | 上面四个页签的全部设置 |
| 插件私有数据目录 | `credential.json`（登录凭证）、`state.json`（今天的轮次记账/冷却/回复记录/封面缓存/这一轮的锁）、`seen.jsonl`（判重表，每条可带一句模型自己写的判断）、`out/<日期>.md`（日报） |
| `%APPDATA%\Cindy\duty\cindy-bili-scroll\` | `config.json` + `state.json`——给前置检查脚本看的镜像。**只有设置和记账，没有凭证、没有日报正文** |

凭证只在插件私有目录，不进 `/kv`、不进对话、不回显；镜像文件里也没有凭证。

## 打包与安装

```
ghost_forge_pack({ dir: "<本目录绝对路径>" })
ghost_forge_install({ dir: "<本目录绝对路径>" })
```

安装时会列出这个插件要的权限：随包 Node 工作进程（有本机文件与网络权限，B站 请求由它在本地发出）、插件私有数据目录（`fs`）、请求新建自动化（`agent.schedule`）。

宿主真正加载的是 `ui/page.html`；`ui/page.template.html` 是同一份页面，生成时只换掉开头那段注释和版本号（版本号取自 `ghost.json`）。生成脚本在仓库里，不随包发布：在仓库根目录跑 `node tools/build-page.cjs`。改页面要改模板再重新生成——只改模板、不重新生成，改动就不会进到实际加载的那份。二维码只在设置页用：它直接加载随包的 `ui/qrcode.js`，卡片里不再内联。

## 开发

仓库根目录**就是**包根目录：`ghost.json` 在最外层，所以 `ghost_forge_pack` 直接指过来就行。代价是打包器没有排除名单，`tools/` 和 `tests/` 也会进到 `.cindy` 包里——约 50 KB，宿主从不加载。想让包瘦下来就得把插件挪进 `plugin/` 子目录，代价是之后每条命令都要多一层路径；这里选了前者。

```
node tools/build-page.cjs           # 用 ui/page.template.html 重新生成 ui/page.html
node tools/sync-charter.cjs         # 用 main.js 里的章程数组覆盖 prompts/*.md
node tools/sync-charter.cjs --check # 只比对，不一致就 exit 1
```

测试不需要装依赖、不联网，纯 Node，每个文件自己打印通过条数：

```
node tests/test-main.cjs        # 用假宿主跑一遍 main.js 的工具分派（主回归套件）
node tests/test-main-gate.cjs   # 设置与闸门契约；第 12 节在把闸门逻辑抄回 main.js 时失败
node tests/test-decide.cjs       # 段表的两种形态是否出自同一次清洗
node tests/test-duty.cjs         # 镜像写入侧的合并规则（跨零点的 hook 计数）
node tests/test-api.cjs          # B站 返回的形状怎么解读
node tests/test-precheck.mjs     # 前置检查脚本端到端
node tests/test-precheck-inbox.mjs
node tests/gate-selftest/run.mjs  # 六个固定闸门场景；传绝对路径可改测已安装的那份
```

改过 `main.js`、闸门或章程之后把这些都跑一遍。`tests/test-duty.cjs` 只写临时目录，不会碰你真实的镜像文件。
